# Report Scheduler backend

The module schedules reports that are defined and generated by Health BI. SSO owns schedule configuration, authorization, execution metadata, recipients, delivery, and audit; it does not duplicate Health BI report definitions.

## Health BI contract

Health BI and Report Scheduler are modules within the Integrated Health Portal,
using the same Keycloak realm. Interactive users retain the portal login and
`data-statistics` module roles; the portal enforces scheduler permissions,
ownership, and district/facility scope before calling Health BI.

Background jobs run without a user session. They use a dedicated confidential
Keycloak service account and short-lived bearer tokens via `client_credentials`.
The backend caches tokens, refreshes before expiry, and retries an unauthorized
Health BI request once with a fresh token. It does not store user refresh tokens
or use admin credentials for report generation.

```dotenv
HEALTH_BI_BASE_URL=https://dashboards.health.go.ug/report-browser
HEALTH_BI_KEYCLOAK_CLIENT_ID=report-scheduler-worker
HEALTH_BI_KEYCLOAK_CLIENT_SECRET=<confidential Keycloak client secret>
HEALTH_BI_TIMEOUT=30s
```

The application base excludes `?report` and `/api/v1`. The token endpoint uses
existing `KEYCLOAK_BASE_URL` and `KEYCLOAK_REALM` settings. Both endpoints must be
reachable from the backend. Integration stays disabled until the application base
and service-account credentials are configured.

In the shared Keycloak realm:

1. Apply the RBAC seed to create `data-statistics:report_scheduler_service`.
   This service role grants no portal user permissions and is not a launcher role.
2. Create confidential OpenID Connect client `report-scheduler-worker` with
   client authentication and service accounts enabled. Disable standard flow,
   implicit flow, and direct access/password grants.
3. Assign only `data-statistics:report_scheduler_service` to its service account.
   Limit role scope to that role and add an audience mapper including client
   audience `data-statistics` in access tokens.
4. Store its generated secret in `HEALTH_BI_KEYCLOAK_CLIENT_SECRET` on the portal
   backend. Do not reuse the admin client or expose this secret to the frontend.

Health BI verifies RS256/JWKS, issuer, expiry, audience, authorized party, and the
service role, even with browser `AUTH_MODE=off`. Configure its `KEYCLOAK_URL` to
the public issuer base and `KEYCLOAK_REALM` to the shared realm, plus:

```dotenv
SCHEDULER_KEYCLOAK_CLIENT_ID=report-scheduler-worker
SCHEDULER_KEYCLOAK_AUDIENCE=data-statistics
SCHEDULER_KEYCLOAK_ROLE=report_scheduler_service
SCHEDULER_ARTIFACT_SIGNING_KEY=<Health BI-only random secret; at least 32 characters>
SCHEDULER_PUBLIC_BASE_URL=https://dashboards.health.go.ug/report-browser
BASE_PATH=/report-browser
```

The signing key is only for artifact download capabilities, not API authentication;
it is not shared with the portal. Migrate the old `SCHEDULER_SERVICE_API_KEY` value
into `SCHEDULER_ARTIFACT_SIGNING_KEY` to preserve existing download signatures,
then remove the old API-key setting. The portal no longer uses
`HEALTH_BI_API_TOKEN` or `HEALTH_BI_AUTH_HEADER`. Health BI also needs its app-state
database and Chrome/Chromium for PDF exports.

The integration currently expects:

- `GET /api/v1/reports`
- `GET /api/v1/reports/{id}`
- `GET /api/v1/reports/{id}/parameters`
- `POST /api/v1/reports/{id}/generate`
- `GET /api/v1/report-jobs/{jobId}`

Responses can be returned directly or in a `{ "data": ... }` envelope. Generation is modeled as asynchronous; Health BI returns a job and the SSO module polls/querys its status and artifact URL.

The adapter advertises `pdf` and `csv` exports. Report detail includes
`metadata.periodStrategies`; the form and backend validate the selected period
against that list. An empty list means the report has no supported calendar period.
Periods must use `Africa/Kampala`; daily periods are currently unsupported by
Health BI. Schedule recurrence remains independent of the reporting period.

Jobs use `queued`, `running`, `completed`, and `failed`. Completed artifacts have
signed capability URLs that recipients can download without a service-account token.
Health BI retains jobs/artifacts for seven days; portal inbox records can outlive
that retention. The portal delivery token TTL (default 24 hours) is independent.
The seven-day limit applies to Health BI artifacts stored as external URLs;
longer retention requires copying them into durable storage.

Helm exposes `backend.healthBI` and `backend.reportScheduler`; supply the service
client secret through `backend.secrets.HEALTH_BI_KEYCLOAK_CLIENT_SECRET`, which is rendered in a Secret.
The client secret is never included in frontend configuration or the ConfigMap.

## SSO API

All routes are under `/api/v1/report-scheduler`, require `data-statistics` system access, and enforce scheduler permissions.

- `GET /` - module status
- `GET /reports` - Health BI report catalogue
- `GET /recipients/options?kind=email|group|portal&search=...` - searchable recipient labels and values; requires scheduler create or update permission, returns at most 100 options, and omits disabled users/groups and service accounts. Optional `selected` is a JSON array of up to 100 saved values to retain their labels while searching.
- `GET /report?reportId={id}` - report metadata (supports category paths)
- `GET /reports/{reportId}` - legacy metadata route for single-segment IDs
- `GET /report-parameters?reportId={id}` - report parameter schema (supports category paths)
- `GET /reports/{reportId}/parameters` - legacy schema route for single-segment IDs
- `GET /schedules` - list schedules
- `POST /schedules` - create a schedule
- `GET /schedules/{scheduleId}` - get a schedule
- `PUT /schedules/{scheduleId}` - update a schedule
- `DELETE /schedules/{scheduleId}` - delete a schedule
- `POST /schedules/{scheduleId}/pause` - pause recurrence
- `POST /schedules/{scheduleId}/resume` - resume and calculate the next run
- `POST /schedules/{scheduleId}/duplicate` - create a paused copy
- `POST /schedules/{scheduleId}/run` - run immediately through the normal execution pipeline
- `GET /overview` - scheduler health and owner/scoped-manager operational metrics
- `GET /metrics` - admin observability view; requires `metrics:read` and `report_scheduler:manage`
- `GET /executions` - list execution history
- `GET /executions/{executionId}` - inspect one execution, artifacts, resolved period, and recipient deliveries
- `POST /executions/{executionId}/retry` - retry a failed execution; delivery failures reuse the existing artifact
- `POST /recipients/preview` - validate and resolve configured report recipients
- `GET /portal-reports` - list reports delivered to the authenticated portal user
- `GET /artifacts/{artifactId}/download` - authorize and redirect to the report artifact
- `GET /public/deliveries/{token}/download` - rate-limited expiring email delivery link

Schedule configuration validates Health BI required parameters and output formats, constrains health scope using the authenticated Keycloak district/facility claims, and persists email/portal recipient configuration. Email delivery attaches the generated PDF/CSV through the existing queued email service and includes a secure download link.

The portal fetches the file from Health BI's Keycloak-protected
`GET /api/v1/report-jobs/{jobId}/artifact` endpoint, or reads an existing storage
object. Attachment bytes are persisted as `data_base64` so queue/outbox retries
retain the file. The sender never follows the external recipient capability URL
with its service credentials. Existing schedules receive attachments too,
including schedules previously saved with `outputConfig.deliveryMode=link`.

`EMAIL_MAX_ATTACHMENT_BYTES` bounds downloads and email attachments (default
10 MiB); Health BI's independent artifact cap is 25 MiB. Missing, expired,
oversized, empty, or invalid PDF downloads cause delivery retry/failure instead
of a successful link-only email. Delivery retries reuse the generated job and
never regenerate the report. Deploy the matching Health BI artifact endpoint
before enabling attachment delivery in the portal.

List APIs are bounded to a maximum of 200 rows. `GET /schedules` supports `limit`, `search`, and `enabled`; `GET /executions` supports `limit`, `search`, and `status`; `GET /portal-reports` supports `limit`. Owner and health-context constraints are applied in SQL before the limit.

## Execution engine

The scheduler worker interval is configured with `REPORT_SCHEDULER_WORKER_INTERVAL` (default `30s`). Due schedules are claimed with PostgreSQL `FOR UPDATE SKIP LOCKED`, an execution snapshot is created, and `next_run_at` advances atomically. This prevents duplicate scheduled execution when multiple SSO backend replicas are running.

Health BI jobs that remain asynchronous are stored as `generating`. Polling uses a separate `polling` claim state with `SKIP LOCKED` so only one backend instance can observe completion and perform delivery.

Supported recurrences are daily, weekly, monthly, quarterly, and annual. Timing is evaluated in the schedule timezone (the UI defaults to `Africa/Kampala`). Supported relative reporting periods include current/previous day, week, epidemiological week, month, quarter, and year. The resolved period is stored on the execution record and passed to Health BI as `reporting_period`; the schedule health scope is passed as `health_context`.

After downtime, the worker performs at most one overdue execution for a schedule and calculates the next run from the current time instead of replaying an unlimited backlog. Worker cycles are capped and write heartbeat, cycle timestamps, and the most recent cycle error to `report_scheduler_runtime`.

## Retry and failure handling

Generation and delivery retries are intentionally separate. Health BI generation uses a bounded three-attempt budget with 30-second, 2-minute, and 5-minute backoff. Each recipient delivery has its own attempt count and retry timestamp. Once an artifact exists, delivery retry never regenerates the report.

A terminal failure creates an audit event, emits a critical admin notification, and queues an email to the schedule owner when the owner has a valid email address. Failure notification is idempotent per execution; an explicit manual retry resets the notification marker and retry budget.

Email delivery is considered handed off once the scheduler successfully queues the message into the portal email outbox. SMTP-level retries remain the responsibility of the existing email worker.

## Ownership, RBAC, and health scope

Users with `report-scheduler_access` receive scheduler read/create/update/delete/execute/history permissions and can manage their own schedules and execution history. Cross-owner administration requires `report_scheduler:manage`, which is assigned to `report_admin`.

A manager with an authenticated facility or district health-context claim is restricted to schedules in that same scope, including schedule CRUD, execution history, retries, overview metrics, and artifact downloads. Only an unscoped platform administrator receives global scheduler visibility.

## Artifact and delivery security

Artifact object keys and Health BI artifact URLs are not serialized to the frontend. Authenticated users download through `/artifacts/{artifactId}/download`, where ownership, portal-delivery access, manager permission, and manager health scope are checked before the backend redirects to the underlying storage URL.

Email recipients receive a unique 256-bit opaque delivery token. Only its SHA-256 hash is stored in the database, the token lifetime is configured with `REPORT_SCHEDULER_DELIVERY_LINK_TTL` (default `24h`), and the public resolver is rate-limited per IP. Raw Health BI generation/job proxy routes are intentionally not exposed: report generation must flow through Run Now or scheduled executions so health scope, history, audit, retry, and delivery controls always apply.

`APP_BASE_URL` must be configured when email delivery is used because it is the origin for secure report-delivery links.

## Monitoring

`GET /overview` exposes enabled schedule totals, 24-hour execution/completion/failure counts, success rate, active retries, failed deliveries, execution and delivery status totals, recent failures, and worker heartbeat health. The overview follows the same owner/manager/health-scope rules as schedule management.

The `/metrics` route exposes the same scheduler telemetry for operations tooling but additionally requires `metrics:read` and `report_scheduler:manage`. Worker heartbeat health is derived from the configured worker interval rather than a fixed timeout.

## Database migrations

Migrations `000045_report_scheduler_operational_indexes` and `000046_report_scheduler_runtime_interval` add production indexes for due schedules, polling, retries, portal inbox/history queries, health-scope administration, and configurable worker-heartbeat monitoring.

Migration `000047_repair_report_execution_polling_status` repairs installations
whose applied execution-status constraint excludes `polling`, even though their
migration version is already 42 or later. The worker uses this state to claim
Health BI jobs. The repair preserves records and all existing valid statuses;
it runs through the normal backend startup migrations. Deploy/restart the updated
backend instead of resetting migration history or changing already-applied files.

The PostgreSQL regression check uses a temporary table and leaves application
records untouched:

```sh
psql "$TEST_DATABASE_URL" -X -f scripts/test-report-scheduler-status-migration.sql
```

Run from the repository root. It reproduces the old constraint violation and
verifies the repair, reapplication, rollback compatibility, and invalid-state rejection.

See the [frontend module README](../../../../frontend/apps/report-scheduler/README.md) for development and access setup.

## Generation failures and deleted schedules

Health BI validation/not-found responses (HTTP 400, 404, 422) end the generation
attempt immediately; repeating the same rejected parameters cannot repair them.
Rate limits and server/network failures retain the bounded retry policy. JSON
error messages are decoded before display so report titles remain readable.

Deleting a schedule atomically cancels its active executions and stops pending
or retrying deliveries, preserving execution history. Work already sent to an
email transport cannot be recalled. A late poll/retry update cannot restore a
cancelled execution. Historical executions whose schedule has been deleted have
no Retry action; create a new schedule to run that report again.

Some Health BI report components intentionally show a rolling time window rather
than just the selected period. Those raw SQL components explicitly declare
`schedulerContextTimeFilters` in their Health BI definition. This exemption is
restricted to time dimensions; location scope must still be bound in every SQL
component. District-profile mortality now applies its month filter consistently.
Missing warehouse views/columns require actual warehouse changes in production;
Health BI's `database/testdb` fixtures repair only the synthetic local database.
