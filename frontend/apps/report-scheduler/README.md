# Report Scheduler

Portal module for scheduling reports that are defined and generated by Health BI.

- Frontend: `frontend/apps/report-scheduler`, mounted at `/apps/dwh/report-scheduler`.
- Backend: `backend/internal/features/report_scheduler`.
- Parent system: `data-statistics`.
- Access role: `data-statistics:report-scheduler_access`.

## Implemented capabilities

The current module supports:

- Health BI report catalogue discovery.
- Dynamic Health BI parameter loading.
- Health-context-aware schedules using Keycloak `district` and `facility` claims.
- Output format selection using the formats exposed by Health BI.
- Schedule recipients using direct email addresses, SSO users, and Keycloak groups.
- Searchable multi-select dropdowns for email recipients, recipient groups, and portal users, with optional external email addresses. Saved selections retain their labels when filtering; administrative user/group permissions are not required.
- Group-recipient preview/resolution through the existing email feature.
- PDF/CSV email attachments through the existing queued email service, with a secure download link.
- Portal delivery to authenticated users.
- Secure artifact download links through the configured storage provider.
- Persistent schedules, recipients, executions, artifacts, and deliveries.
- Daily, weekly, monthly, quarterly, and annual recurrence timing.
- Reporting periods constrained by each report's advertised capabilities.
- Schedule edit, pause, resume, duplicate, delete, and Run Now controls.
- Automatic background execution and Health BI job polling with multi-replica database locking.
- Execution history with resolved periods, generation attempt counts, errors, artifacts, and recipient-level delivery state.
- Independent generation and delivery retry/backoff with manual retry controls.
- Terminal failure audit events, administrator alerts, and owner email notifications.
- Operational overview with 24-hour execution, success, failure, retry, delivery, and scheduler-worker heartbeat metrics.
- Health-context-constrained administration for district/facility managers; only unscoped administrators receive global scheduler management visibility.
- SSO-controlled artifact download endpoints instead of exposing object keys or Health BI artifact URLs in API responses.
- Expiring opaque email delivery links with SHA-256 server-side token storage and public endpoint rate limiting.
- Missed-run protection that performs one catch-up execution instead of replaying an unlimited backlog after downtime.
- Server-backed schedule filtering by search and enabled/paused state.
- Server-backed execution filtering by report search and execution status.
- Bounded history/inbox queries to avoid unbounded scheduler UI loads.
- Admin scheduler metrics endpoint for operations tooling.

## Health BI integration

The `dwh_visualization` scheduler adapter uses the application base
`https://dashboards.health.go.ug/report-browser`, within the shared Integrated
Health Portal Keycloak realm. Users retain their
portal session and module permissions. Background jobs use a dedicated backend
Keycloak service account with automatically refreshed bearer tokens. See the
[backend configuration and contract](../../../backend/internal/features/report_scheduler/README.md).

The form loads report detail before saving and offers only supported periods and
formats. The current adapter supports PDF/CSV and whole calendar periods in
`Africa/Kampala`; daily reporting periods are unsupported. Recurrence frequency
is independent of the period being exported. Nested report IDs use query
parameters so category paths survive routing. Additional filters without inline
options are entered as text; the browser API's `optionsEndpoint` is not called
with the scheduler service token.

Health BI artifacts expire after seven days, even if their portal inbox entry
remains. End-to-end verification requires both services, the configured Keycloak service
account, and configured database/email services.

Selecting a report prefills its declared parameter defaults, supported reporting
period, and export format. Saved values and manual edits override defaults;
refreshes do not overwrite them. Changing the report clears its previous
parameters. Filters without declared defaults remain blank. Health BI's
`defaultValue` and `metadata.noDefault`/`hideNone` settings control prepopulation.

## Development

Run from `frontend/`:

```sh
npm run dev:mf:report-scheduler
npm run build -w @moh-sso/report-scheduler
npm run preview:mf:report-scheduler
```

The local microfrontend uses port 4115 and relies on the portal login session.

## Access

The backend requires the `data-statistics` parent system plus the relevant granular scheduler permission. Apply/sync the RBAC seed after permission changes:

```sh
go run ./cmd/cli system-rbac validate --file config/system-rbac.seed.yaml
go run ./cmd/cli system-rbac seed --file config/system-rbac.seed.yaml
```

Existing installations should assign `data-statistics:report-scheduler_access` to authorized users/groups and refresh their sessions.
The `report_admin` role adds `report_scheduler:manage` for cross-owner administration, subject to the authenticated district/facility health context when one is present.

## Frontend permissions

The scheduler uses the shared `@moh-sso/auth` authorization state. Both module
entry and the independently mounted schedule form deny access without
`data-statistics` system access and `report_scheduler:read`. Protected requests
are skipped when their permission is absent; hiding controls alone is insufficient.

| Permission                 | Frontend access                                                             |
| -------------------------- | --------------------------------------------------------------------------- |
| `report_scheduler:read`    | Own schedules, portal inbox, authorized artifact downloads                  |
| `report_scheduler:create`  | Create and duplicate schedules, recipient directory and preview             |
| `report_scheduler:update`  | Edit, pause and resume schedules, recipient directory and preview           |
| `report_scheduler:delete`  | Delete schedule controls and confirmation                                   |
| `report_scheduler:execute` | Run now; retry when execution history is also accessible                    |
| `report_scheduler:history` | Execution tab, expandable details, health strip and summary metrics         |
| `report_scheduler:manage`  | Broader ownership scope from the backend; does not grant action permissions |

Read-only users do not subscribe to history/health endpoints, see mutation
controls, or load the recipient directory. Revoking history access returns an
open history tab to schedules and stops detail polling. Revoking create/update
access unmounts an open form. Backend permissions, ownership, and health-context
checks remain authoritative for every request. Portal downloads use `read` and
server-side recipient authorization; no additional download permission is required.

Run `node --test scripts/report-scheduler-permissions.test.mjs` from `frontend`
for permission, rendered-control, query-subscription, and retry boundary checks.
